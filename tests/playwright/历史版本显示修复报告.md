### 2. 根本原因发现

**关键问题**：签入时归档了原版本，导致历史版本查询不到！

#### 签出-签入流程分析

**签出时** (`IetmDataModuleServiceImpl.java:334-443`):
1. 创建工作副本（inWork +1）
2. 将原版本标记为历史版本：`is_latest='1'` → `'0'`
3. 将更早的历史版本归档：`status='1'` → `'0'`
4. **原版本保持** `status='1'`

**签入时的致命BUG** (`IetmDataModuleServiceImpl.java:556-580`):

**结果**：
- 最新版本：`is_latest='1'`, `status='1'` → **显示** ✅
- 原版本：`is_latest='0'`, `status='0'` → **不显示** ❌（被归档）

**每次签入都归档原版本 → 历史版本列表永远只有1个版本！**

## 🎯 修复原理

### 为什么删除这段代码是安全的？

**原代码的注释说明**：
> 避免下次签出时唯一约束冲突：
> - 签出时原版本被降级为 `is_latest='0', status='1'`
> - 下次签出时，会再次尝试降级当前版本，但已有原版本 `is_latest='0', status='1'`
> - 违反唯一约束：`(sns, info_code, ..., status='1', is_latest='0')` 只能有1条

**但是**：签出时已经解决了这个问题！

**签出逻辑** (`IetmDataModuleServiceImpl.java:418-433`):
```java
// 将该DM所有历史版本改为 status='0'（归档）
LambdaUpdateWrapper<IetmDataModule> archiveWrapper = new LambdaUpdateWrapper<IetmDataModule>()
        .eq(IetmDataModule::getSns, originalDm.getSns())
        .eq(IetmDataModule::getInfoCode, originalDm.getInfoCode())
        // ... 其他DMC字段
        .eq(IetmDataModule::getStatus, "1")
        .eq(IetmDataModule::getIsLatest, "0")  // 🔑 只归档历史版本
        .ne(IetmDataModule::getId, originalDm.getId())  // 排除当前版本
        .set(IetmDataModule::getStatus, "0");  // 归档

this.update(archiveWrapper);
```

**说明**：
- 签出时已经将**更早的**历史版本（`is_latest='0'`）归档为 `status='0'`
- 只保留**当前版本**作为新的历史版本（`is_latest='0', status='1'`）
- 下次签出时，会再次归档这个"当前变历史"的版本
- **因此签入时无需再归档！**

## 📝 总结

### 问题原因
签入时错误地归档了原版本（`status='1'→'0'`），导致历史版本查询条件 `status='1'` 查不到已归档的版本。

### 修复措施
删除签入时的归档逻辑，保留原版本为 `status='1'`，让它正常出现在历史版本列表中。

### 安全性
签出时已经处理了唯一约束问题，签入时归档是多余的且有害的。

### 影响范围
- ✅ 修复后，历史版本列表将正常显示所有版本
- ✅ 不影响其他功能
